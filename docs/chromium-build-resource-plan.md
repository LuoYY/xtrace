## 1. 结论与当前机器约束

**推荐方案：单构建协调者 + 两档任务并发 + 后台调度 + 单 linker/限制 linker 内部线程 + 磁盘/压力停止门；复用现有增量产物，B 完成后再构建 A。**

降低占用和缩短一次全量构建的墙钟时间存在取舍：`-j2` 通常不会比满核首构建更快，但可减少 swap、前台卡顿、重复中断和返工。真正的加速重点是减少重编、保留有效对象、先验证小目标、避免两套构建争抢，以及在合适阶段引入编译缓存。

## 2. 磁盘门已满足，保留产物并持续检查

### 2.1 恢复门槛（本方案的初始保守预算，不是 Chromium 官方定值）

- A/B 完整 release 续编前：输出所在文件系统 **至少 60 GiB 可用**，同时核对预计剩余对象、Framework 链接临时文件和验证输出预算；估计不够时提高门槛。
- 运行中低于 **30 GiB**：停止派发/中断受管构建并报告，不等到 ENOSPC。
- 首次恢复只跑 B；完成且复测后再决定 A 的资源窗口。
- F5 每次测量设输出体积与总实验预算，建议初始 `1 GiB/次、10 GiB/整组`；超额应明确失败并调整负载/容量预算，不采样删事件后仍声称完整。

最新实测约 321 GiB（用户报告 345.42 GB），已满足空间门槛；18/109 GiB 仅保留为历史。**工程师无需等待或继续磁盘清理，应直接推进功能整改与资源控制。** 空间充足仍不代表已获 A/B 恢复授权、限流已接线或剩余工作预算已测准。不能由“B 文件已存在”推断它是当前源码完整链接的产物，暂停构建目录可能混有旧最终文件与新对象。

### 2.2 空间不足时的处置预案（当前不执行）

当前空间已充足，以下不是工程师的立即待办；仅在后续实时检查跌破预算时使用，清理/迁移仍须授权。

1. 清点 validation 中已结案运行的 profile、重复 trace 和旧产物，形成清单：路径、大小、是否被验收引用、是否可重现、是否有备份。
2. 先将必须保留的失败证据/最终证据归档到**用户批准的位置**，校验摘要和可读性，再由用户确认允许删除哪些本地副本。不要删除唯一原始失败证据。
3. 同一 APFS 卷上简单 mv/clone 不会释放所需空间；本盘压缩也需要额外空间，不能盲目执行。外接 SSD 迁移要先验证文件系统/工具链兼容、绝对路径依赖与增量命中，不能保证零重建。
4. 保留 `.ninja_log/.ninja_deps`、有效 obj/gen、两套正在续编的输出目录。**不执行 `ninja -t clean`、不清空 out、不重下载源码**。
5. validation 历史快照约 11 GiB；以首次剩余 18 GiB 计算，单靠它不足以达到 60 GiB。当前约 321 GiB 已满足门槛，无需再清理；未来不足时由用户选择可归档空间或更大构建盘，不得擅自扫描/删除用户其他项目。

## 3. 限流：任务数、linker 内线程、系统压力分开控制

### 3.1 两档配置

| 档位 | 场景 | Ninja | 调度 | linker |
| --- | --- | --- | --- | --- |
| interactive（默认） | 用户在电脑工作 | `-j2 -l3 -k1` | `/usr/sbin/taskpolicy -b` + `nice -n 10` | 同时最多 1 个，内部线程初始 2 |
| idle（用户授权空闲窗口） | 前台轻载/离开电脑 | `-j4 -l6 -k1` | 同上 | 同时最多 1 个，内部线程初始 2；有实测再升档 |

不默认 `-j10`、不默认让 Ninja 猜 20、不同时运行 A/B、不使用 `-k0` 长时间继续已知失败后的全图。

**边界必须说清：**

- `-j` 限制的是 Ninja 同时运行的命令数量，不是 CPU 百分比；一个 linker/Rust/Swift 命令可能再开线程。
- `-l` 根据系统负载限制新任务，不停止已经运行的任务，也不是内存限额；低负载阈值会降低构建吞吐，属前台优先的有意选择。
- `taskpolicy -b` 与 nice 是调度/QoS 优先级，不是“锁定能效核”，不能保证固定 CPU 或 RAM 上限。
- macOS 本机这些机制不能提供整个构建进程树的硬内存/CPU配额；若用户要求严格隔离且单链接仍干扰前台，选择独立 macOS arm64 构建机/VM 的资源边界。远端发送源码、日志与凭据必须另行获批，不能自动启用 remoteexec。

### 3.2 linker 的明确接线

已确认固定源码支持：

- `build/toolchain/concurrent_links.gni:17–23` 声明 `concurrent_links`；`:175–179` 允许非 ThinLTO 显式设置。
- 本机 `use_thin_lto=false`，因此 A/B 可统一设置 **`concurrent_links=1`**；若未来打开 ThinLTO，不能照搬此参数，该文件有显式断言。
- bundled `ld64.lld --help` 支持 **`--threads=2`**，默认使用所有可用硬件线程；Ninja -j1 不自动限制这些内部线程。

执行层对 `build/config/compiler/BUILD.gn` 的 linker 配置增加一个小的、可追溯的项目控制项（建议名 `xtrace_lld_threads`，**目前不存在**）：默认 0 保持上游，mac+lld 时非零才加 `-Wl,--threads=N`。该变更经 Chromium 补丁交付，A/B 设置同值 2；不要假称已有通用 `extra_ldflags` GN 参数，也不要编辑生成的 Ninja 文件。

只改调度池应不改编译输出；增加 linker 线程参数通常使相关链接命令失效重跑，不应导致所有 C++ 编译失效。执行前用 `ninja -n -d explain chrome` 核对计划，若出现大范围重编，先找影响命令的真实变化，不强行开跑。最终 A/B 必须在同一新配置下重新链接并绑定摘要。

Apple 工具链中的 Swift driver 还会按 CPU 数派生子线程（`build/toolchain/apple/swiftc.py:440–454`）；如果实际剩余图包含此类命令，限制或单独安排其阶段，不能只管 C++ 与 linker 就声称硬限额已建立。

### 3.3 受控续编命令形状

**以下是用户允许恢复且完成空间/调度接线后的命令模板，本轮未执行。** 从 XTrace 根目录运行，B 成功后再手动将 OUT 换成 A；不要用后台并发执行两份。

```bash
ROOT=/Users/luoyy/work/github/GitHub/xtrace
OUT="$ROOT/chromium/src/out/XTrace-release"
LOG=$(mktemp "$ROOT/chromium/src/out/XTraceIntegration/validation/resource-build-XXXXXX")
if env -u GOROOT -u GOTOOLDIR \
    DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
    /usr/sbin/taskpolicy -b /usr/bin/nice -n 10 \
    "$ROOT/chromium/src/third_party/ninja/ninja" \
    -C "$OUT" -j 2 -l 3 -k 1 chrome > "$LOG" 2>&1; then
  BUILD_EXIT=0
else
  BUILD_EXIT=$?
fi
printf '%s\n' "$BUILD_EXIT" > "$LOG.exit-code"
```

模板中的 QoS 和并发只能软限流；完整自动资源停止门属于下一节待实施协调器。在协调器尚未交付前，不能把该命令宣传为“不会占用过多资源”的硬保证。日常低负载复验不与编译并行，性能测量时彻底停止编译，避免污染时间/RSS对照。

## 4. 执行层需要交付的资源协调器

优先修改现有 `scripts/build_xtrace_release.sh`，必要时加入一个跨脚本共享的本地协调器，不在 out 下维护唯一脚本。

### 4.1 参数和职责

- `BUILD_PROFILE=interactive|idle`：默认 interactive，对应第 3 节；允许显式 `JOBS`/`LOAD_LIMIT`，拒绝非法值及 `JOBS=0`（Ninja 中代表无限）。
- `GEN_ONLY=1`：只生成图，不启动 Ninja；`RESUME=1`：默认不重写已确认的 args，仅执行增量图。**这些参数当前脚本未实现**，不可直接传后以为已经生效。
- 尊重显式 `NINJA_BIN`，当前 `:35` 会被 tree-local ninja 无条件覆盖，应修正。输出使用哪个 executable、argv、args 摘要和并发档位。
- 项目级排他锁覆盖 Integration、P4D8、release-A/B；记录 PID、进程开始时间、输出目录、命令。其他实例拒绝启动。锁过期先核验，不按文件存在盲删、不杀不属于本项目的进程。
- 子进程置独立进程组，记录退出码和中断原因。监控只追踪本次受管组及其后代，不匹配全系统名称批量 kill。

### 4.2 初始监控阈值

每 5 秒采样、日志有界；以下是初始预算，需要一轮小任务实测后再调，不是已经获得的性能承诺。

| 指标 | 初始处置 |
| --- | --- |
| 输出盘可用 <30 GiB | 立即要求受管组中断，不自动恢复 |
| 系统 memory pressure warning/critical 持续 | 停止构建并报告，优先保住前台 |
| 构建进程树 RSS 估计 >12 GiB，连续两次 | 暂停本轮并报告；单次链接需要更高预算时另议 |
| interactive 构建进程树 CPU >350%，持续 30 秒 | 视为多线程子任务突破预算，停止并定位；不是每秒锯齿停/开 |
| swap 增量持续增长或出现热降频 | 记录窗口差值并降档/停止，不能用开机以来累计 swap 值判断本次 |
| 用户手动暂停 | 高优先级立即停止本轮，不自动重启 |

进程树 RSS 会重复计算共享页，只作为保守阈值，不称作精确物理内存占用。CPU 百分比按单核 100% 口径；watchdog 是事后停止机制，不能保证瞬时峰值不超限。降低单任务峰值失败时，转移到独立机器优于在前台电脑硬撑。

### 4.3 暂停与续编

- 正常暂停：对协调器管理的构建进程组发送 SIGINT，让 Ninja/子任务退出；保留成功生成的对象与依赖库。中断的少量输出按 Ninja 规则在续编时重建。
- 不使用 SIGSTOP 长期冻结整个重链接：它仍占用内存；也不只停 Ninja 父进程让子进程继续满载。
- 若 SIGINT 未结束，报告卡住进程；只在本次授权范围内处理受管后代，不自动升级为全系统 kill 或删锁/删 out。
- 续编仍用同一目录和匹配参数，由用户显式恢复；不重新同步源码，不清除 `.ninja_log/.ninja_deps`。因依赖损坏必须删单个自产中间件时，先定位原因，不以 clean 作为常规修复。

## 5. 加速方案：减少工作量，不降低验收标准

### 5.1 本轮立即采用的工作排序

1. **零编译先行**：修 F5 CDP sessionId 转发、完成值/超时/清理、测量 schema 和输出预算。用 fake transport 单测、现有 Integration 二进制作小负载驱动自检；不等 release 成功才发现驱动不可用。
2. **V8 生命周期修复 → 既有 `XTraceP4D8` d8 增量目标**：先验证真实弱回收、存活对象 GC 稳定、丢弃对象回收和多 isolate 销毁。原 P0 `XTraceD8Verify` 只读，绝不重建。
3. **Blink stop/Worker 销毁与 parser 修复 → Integration component 增量 chrome**：先命中的单目标/单测，再必要的浏览器反例；不在每处小改后同步重建 release A/B。
4. **功能源冻结**：补丁/驱动/参数确定，先重放校验和静态检查。
5. **B 先、A 后**：复用当前 B 增量进度，验证其包含最终源码；再补 A 首构建。不能利用旧 B 的 app 存在当作当前 B 已完成。
6. **A/B/C 测量**：构建全部停止、环境稳定，每轮独立目录，先校验正确性再统计性能。

P5 设计可在等待资源窗口时推进，但不能在缺少范围控制和生命周期正确性的 P4 上落 C++。用户暂停全量编译是资源决策，不是取消性能验收，也不是功能质量豁免。

### 5.2 保留现有 GN 口径，避免代价最大的“优化”

- 当前 release 是 `is_debug=false/is_component_build=false/symbol_level=1`。为了续编不重置 symbol/component/PGO/LTO；这些变化可能使大量目标失效，反而更慢。
- Integration 保持 component 供开发迭代；release 只在阶段冻结后用于性能/发布验证。不把 component 性能冒充 non-component release 结果。
- A/B 参数归一比较必须忽略注释和顺序，而不是字符串相等；仅 observer 编译位不同，其他代码生成、符号、tracing、linker 并发设置相同。
- 当前 `use_reclient=false` 出现在脚本与 args，但有效开关是 `use_remoteexec=false`。执行层统一使用固定版本支持的参数并加 `--fail-on-unused-args`，先检查有效值等价，不借机更换远程工具链。
- `ninja -n -d explain <target>` 用于预测失效范围；`-t query/-t commands` 查依赖与编译命令。不要为了“只编一个文件”跳过最终完整 chrome 成功退出的门槛。

### 5.3 编译缓存（第二优先级，不现在临时安装）

固定树有 `build/toolchain/cc_wrapper.gni`，支持 ccache/sccache，与 use_remoteexec 互斥。推荐在**下一次主动重建窗口或独立构建机**评估本地 ccache/sccache：

- 首次空缓存不节省必编译任务，还增加磁盘写入；首次仅剩 18 GiB 时不应增加大缓存。即使收尾空间已回升，也要单独预算缓存容量，不因空间暂时充足就中断现有增量进度。
- 插入 `cc_wrapper` 会改变编译命令，可能触发大范围重编；先在小目标量化 cold/warm 命中，再决定是否让当前 A/B 付出这笔成本。
- 编译器版本/参数不同的 A/B 翻译单元应自然 miss，不开启会弱化正确性的 sloppiness。相同 Blink/content 单元是否跨输出目录命中要实测，不承诺 A 全命中 B。
- 缓存放用户批准的磁盘，设独立容量上限；它不替代已有 obj，不删除原始证据腾缓存。
- 若配置缓存，A/B 配置一致，记录工具版本、命中率、cold/warm 时间、磁盘和 CPU 代价。不要同时引入远程构建、工具链升级和性能代码修复三个变量。

### 5.4 本机仍不合适时

如果达到磁盘门槛后，单 linker 的最低并发仍使前台卡顿，推荐用户提供独立 macOS arm64 构建机，同固定上游、补丁、Xcode/SDK/Clang 做 A/B 构建；两套性能样本必须在同一运行环境测试并披露环境。当前无远端配置或授权，本方案不自动上传代码、不假定远程编译可用，也不以 Linux 产物替代 macOS 验收。
